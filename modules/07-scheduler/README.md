# 07 — Scheduler

**Thesis.** Go multiplexes cheap goroutines (G) over OS threads (M) through
`GOMAXPROCS` logical processors (P), with work stealing, a netpoller that parks
I/O-blocked goroutines without holding a thread, and (since Go 1.14)
asynchronous preemption so a tight loop no longer starves the scheduler. The
practical consequences are measurable: goroutines are cheap enough that
oversubscription *helps* latency, and the one production pitfall — `GOMAXPROCS`
versus a container CPU quota — was itself fixed in Go 1.25.

## Latency under load

`cmd/latency` submits 200,000 CPU-bound tasks to a pool and reports task
completion-latency percentiles at three worker counts:

<!-- BEGIN:snippet go-pool -->
```go
// cpuWork is a small, fixed CPU-bound task (no allocation, no I/O), so a pool of
// these measures pure scheduling behavior.
func cpuWork() float64 {
	x := 0.0
	for i := range 2000 {
		x += math.Sqrt(float64(i))
	}
	return x
}

// PoolLatencies submits nTasks to a pool of `workers` goroutines and returns
// each task's LATENCY: the time from submission to completion. With more tasks
// than logical processors, tasks queue, and the tail (p99) shows the scheduler's
// queueing under CPU-bound load.
func PoolLatencies(workers, nTasks int) []time.Duration {
	tasks := make(chan time.Time, nTasks)
	lat := make([]time.Duration, nTasks)
	var wg sync.WaitGroup
	var idx int64
	var mu sync.Mutex

	for range workers {
		wg.Add(1)
		go func() {
			defer wg.Done()
			for submitted := range tasks {
				_ = cpuWork()
				d := time.Since(submitted)
				mu.Lock()
				lat[idx] = d
				idx++
				mu.Unlock()
			}
		}()
	}
	for range nTasks {
		tasks <- time.Now()
	}
	close(tasks)
	wg.Wait()
	return lat
}
```
<!-- END:snippet go-pool -->

Measured (non-deterministic; regenerated by `scripts/sched-bench.sh`):

<!-- END:file measured -->

Reading it: under-provisioning (`workers=2`) blows the tail from microseconds to
tens of milliseconds. But *oversubscribing* (4x `GOMAXPROCS`) does not hurt and
even lowers p50 — because a goroutine is cheap, a submitted task finds a ready
worker sooner, and the runtime folds them onto the same P count. The "one thread
per core, never more" rule for OS threads does not transfer to goroutines.

The cross-language block shows the counterpart: for an *embarrassingly parallel,
CPU-bound* sweep, all five runtimes land within ~15% of each other. The
scheduler model barely matters when the work is pure CPU and evenly divisible;
it matters for latency under contention, for cheap-task scaling, and for I/O
concurrency — not for raw parallel throughput.

## GOMAXPROCS and cgroup quotas

The classic production bug: a Go binary in a container with a 2-CPU quota on a
many-core host used to set `GOMAXPROCS` to the host core count, oversubscribing
badly, and teams reached for `uber-go/automaxprocs`. **Go 1.25 fixed this in the
runtime**: `GOMAXPROCS` now defaults to the cgroup CPU bandwidth limit when one
is set. On this macOS machine there is no cgroup, so `GOMAXPROCS` is the core
count (14); the containerized behavior cannot be reproduced here, which is an
honest limit of this measurement, but the change and the mechanism are the
point. `GOMAXPROCS` remains overridable, and `automaxprocs` is now largely
redundant on 1.25+.
